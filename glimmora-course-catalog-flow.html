Proposal under review

What you proposed

Two flows live side-by-side under the "Courses" module. The first defines the course; the second schedules it.

Flow A — Course Catalog

Create a course

No need to add department, year, etc. at this stage. Just the design-time identity of the course.

course name course id syllabus regulation
Flow B — Section Course

Add course to section

Pick the catalog course and assign it to a specific cohort. One click and it's live.

academic year code year sem branch section

Verdict

The two-tier idea is conceptually correct — this is exactly how Banner, PeopleSoft, and Workday Student model courses. The bones are right. The edges have nine specific gaps that will surface as bugs the moment a real university uses the system. The rest of this document walks through each one.

Foundation

The two-tier model — visualised

"Catalog" is what the course is. "Offering" is when, where, and to whom it's taught. One catalog row produces many offering rows over time.

Three offerings, one catalog row. The catalog row is the source of truth for syllabus and credits; the offerings know which cohort and term they belong to.

Issue 1

Department on the catalog row

The proposal says "no need to add the dept" on catalog. In an Indian university context, this is risky.

01 Every course has an owning department, even when taught cross-department Medium

"Engineering Mathematics" is owned by the Maths department but taught to CSE, ECE, and MECH students. "Communication Skills" is owned by Humanities but taught to everyone. The owning department determines:

  • Who is accountable for syllabus updates
  • Whose HOD can edit/approve catalog changes (department-scoped permissions)
  • Department-level reports — "all courses owned by CSE", "credits offered per dept"
  • Faculty assignment defaults — usually pick faculty from the owning dept first
Wrong way

Drop department entirely

Every catalog row floats free. No accountability, no scoped permissions, no dept reports.

Right way

Optional but recommended

Add owning_department_id as nullable. Most courses fill it; cross-cutting platform courses (e.g., "Yoga") can leave it blank.

Issue 2

Regulation versioning

"Regulation" in Indian universities means the curriculum version approved by the academic council — R20, R21, R22, etc. When the regulation changes, syllabus and often credits change. Putting regulation directly on the catalog row creates duplicate rows.

02 "Regulation" as a flat field on catalog forces row duplication High

The duplication problem

If CS101 exists under R20, R21 and R22, you end up with three nearly-identical catalog rows. Editing the course name on one doesn't update the others. Reports show three "different" courses that are conceptually the same.

Two ways to handle this

Two strategies for handling regulation changes
Option A — Versioned catalog

Recommended for scale

Course is the identity (code + name). CourseVersion holds (regulation, syllabus, credits, effective_from, effective_to). Offering points to a specific version.

Pro: No duplicate rows. Renaming "CS101" updates everywhere.

Con: One extra table, slightly more complex queries.

Option B — Composite key

Recommended for MVP

(course_code, regulation_id) is the natural key. Accept duplicate rows because each regulation truly is a different course structure.

Pro: Simpler. One table. Easier to ship.

Con: Editing common fields (name) means editing N rows.

Recommendation

Start with Option B for MVP. Migrate to Option A in phase 2 once you have 2–3 customers and real regulation churn data. Don't over-engineer on day one.

Offering dimensions — naming collisions

Issue 4

"Click add course → assigns directly" hides three operations

When a section-course is "assigned," three distinct things happen. The current proposal does step 1 and silently does step 3, but step 2 is missing — and step 2 is what makes the offering operational.

04 Faculty assignment is missing — offerings will be created in a non-operational state High
sequenceDiagram autonumber actor UA as University Admin participant UI as Add Course Drawer participant DB as Database participant FP as Faculty Portal participant SP as Student Portal UA->>UI: Pick catalog course + section + year + sem UA->>UI: Click "Add Course" button UI->>DB: 1. CREATE course_offering row UI->>DB: 3. AUTO-ENROLL all students from section Note over UI,DB: Step 2 missing — no faculty assigned! UI-->>UA: "Course added" toast rect rgba(254, 226, 226, 0.5) FP->>DB: Faculty checks "my courses" DB-->>FP: Empty — nobody is assigned SP->>DB: Student checks "my courses" DB-->>SP: Course visible but "Faculty: TBD" end
Current flow leaves the offering in a non-operational state

The three operations spelled out

  1. Create the offering"CS101 will be taught in 2025–26 Sem 1 to CSE-A." Pure scheduling row.
  2. Assign faculty to teach itWithout a faculty user linked, the offering is dead — no one shows up to teach, faculty portal renders nothing, student portal shows "TBD."
  3. Enroll studentsFor core courses: all students in the section are auto-rostered. For electives: students self-select (see Issue 5).

Recommended UX

Same drawer. Three sections: Course & Section, Faculty, Enrollment Mode. Faculty can be optional at create-time (mark offering as draft) but the UI must surface "0 faculty assigned" as a warning chip on the offerings list so it doesn't get forgotten.

Issue 5

Core vs Elective — the section-based assign model breaks for electives

"Pick branch + section → all students get the course" is correct for core courses. For electives, two students in the same section pick different courses. The model needs to handle both.

Different enrollment paths based on course type

What needs to change

  • Add course_type on catalog — values: Core, Programme Elective, Open Elective
  • Add capacity on offering — for electives, max students who can enroll (electives often have lab/seat limits)
  • Add an "Elective Selection" flow in the student portal — students see eligible electives within their elective slot and submit choices ranked by preference
  • Add an "Elective Allocation" view for university admin — see who picked what, allocate by rules (preference / GPA / lottery)

If you skip this

Either students see electives they didn't choose, or they don't see the ones they did. Both are immediate trust-killing bugs the moment a real semester starts.

Issue 6

Course components (L:T:P) are missing entirely

Indian engineering courses are commonly described in L:T:P notation — Lecture : Tutorial : Practical hours per week. A course like "3:0:2" means 3 hours of lecture and 2 hours of lab each week. These are taught separately and often by different faculty.

06 No way to model lectures, tutorials, and labs as separate teaching components High

Why it matters operationally

  • Lab sections are often smaller than lecture sections — a 60-student lecture splits into three 20-student lab batches
  • Different faculty often teach lecture vs lab — the senior prof handles theory, an assistant prof handles labs
  • Attendance and grading rules differ — labs have continuous assessment, theory has end-sem exams
  • Timetable engines need this — you can't schedule a "course" without knowing it has 3+2 hours split into different rooms

L:T:P stored on catalog; components instantiated per offering

Catalog defines the L:T:P breakdown and total credits. Offering has child OfferingComponent rows — one for lecture, one or more for lab batches, optionally tutorial. Each component has its own faculty assignment, schedule slot, and room.

For MVP, you can collapse this to a single component per offering and add the breakdown later — but make sure the course_offering table has child offering_component from day one, even if MVP only ever creates one row per offering. Otherwise this becomes a schema migration on a table with student data.

Issue 7

Course "id" vs course "code" — keep them separate

07 Conflating display code with primary key Low

The proposal lists "course id" as a field the user enters. That's actually two fields:

Field 1

course_code

Human-readable. Entered by the university admin. Examples: CS101, MATH202, HUM304.

Unique within a regulation (not globally — see Issue 2).

Field 2

id (UUID)

System-generated primary key. Never shown to users. Used in URLs, foreign keys, API calls.

Always unique. Never editable.

In the UI, show course_code. Key on id. If you let the admin edit the code later (renaming "CS101" to "CSE101"), the UUID stays stable and nothing breaks.

Edit propagation rules — past offerings must keep their snapshot

Why this matters legally

A student's transcript says they completed "CS101" with syllabus X. Years later, an employer or an audit asks what was in syllabus X. If you've silently overwritten the catalog with syllabus Y, you can't answer. This is a compliance and audit-trail issue, not just a UX one.

Two acceptable rules

Strict (Option A)

Versioned catalog

Every edit creates a new version. Past offerings reference the old version forever. New offerings reference the new version.

Pragmatic (Option B)

Snapshot on offering create

When an offering is created, copy the syllabus into the offering row. Future catalog edits don't affect existing offerings. Simpler, slightly more storage.

For MVP, Option B is good enough. Just make sure the snapshot fields (syllabus_snapshot, credits_snapshot) exist on the offering table from day one.

Issue 9

Roles & permissions on courses

The transcript says "four active personas." With four, the university admin becomes a bottleneck — every CS dept, every Maths dept, every Civil dept catalog edit goes through one person. Worth re-opening whether HOD is a fifth persona or a permission flag.

09 Permission scope on Catalog vs Offering needs to be explicit Medium
Persona Course Catalog Section Course (Offering) Notes
Super Admin No access No access Stays out of academic data; only manages universities themselves
University Admin Full CRUD Full CRUD Owns all academic master data within their university
HOD (if added as 5th) CRUD within own dept CRUD within own dept Removes the bottleneck; enables dept-scoped governance
Faculty Read-only Edit own assigned offerings only Can manage course content, materials, attendance, grades within their offering
Student No access Read enrolled offerings only Sees the syllabus snapshot, schedule, faculty, materials

Decision needed before build

Lock in 4 vs 5 personas. If we keep 4, university admin manages every dept's catalog manually — fine for a 200-course university, painful for a 2000-course one. If we add HOD as a 5th, we need a department_id on the user record and dept-scoped middleware on every catalog/offering API. The model in this doc supports both — but the UI needs to know which one we're shipping.

Action plan

Recommended next steps

Before Shaik writes any code on the course module, lock down these seven decisions. None of them block individually — but each one will cause a refactor if discovered after build.

  1. Sketch and approve the ER diagram Course → CourseOffering → Enrollment, plus FacultyAssignment and OfferingComponent. 30 minutes of modeling saves weeks of rework. Use the diagram in section 3 as the starting point.
  2. Decide regulation strategy — Option A (versioned) or Option B (composite key) For MVP: Option B. Mark this in the schema and revisit at phase 2.
  3. Add course_type on catalog as a first-class field Values: Core, Programme Elective, Open Elective. Without this, the elective flow becomes a refactor in phase 2.
  4. Add the snapshot fields on offering from day one syllabus_snapshot, credits_snapshot, regulation_snapshot. Even if MVP just copies them at create time, having them in the schema makes Issue 8 a non-event.
  5. Add faculty assignment to the same drawer as "add course to section" Don't make it a separate page nobody clicks. Mark offerings without faculty as draft and surface a warning chip in the offerings list.
  6. Add child offering_component table from day one Even if MVP creates exactly one component per offering. Adding this later means migrating a table that already has student enrollment data.
  7. Re-confirm 4 vs 5 personas with Tamilarasi HOD-level scoping is the difference between "university admin micromanages everything" and "HODs own their dept catalogs." Decide before building permissions middleware.

Bottom line

The two-tier idea (catalog vs offering) is correct. The edges — regulation versioning, electives, components, faculty assignment, edit propagation — are where real universities differ from a generic SIS. Get these right before code, and the build is straightforward. Skip them, and every one becomes a customer-visible bug in the first semester of use.
