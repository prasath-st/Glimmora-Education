Academic Structure Proposal

Current problems with the University Admin flow and the proposed solution for MVP

Part 1

Current Structure & Problems

The existing data model is flat — entities are disconnected. There's no hierarchy linking academic years, semesters, programs, and courses together.

Current Data Model (Flat & Disconnected)

University Admin
SemestersCreated standalone
CoursesLinked to 1 semester
UsersName, Email, Role, Dept
No Academic Year
No Program / Degree
No Batch Concept
No Student ID

⚠ Semesters Float Without Context

Semesters are created standalone with no parent academic year. The admin doesn't know which year a semester belongs to or how semesters relate to each other.

Example: "Spring 2026" exists but — is it Year 1 or Year 3 of a student's program? No way to tell.

⚠ No Program / Degree Concept

There's no way to represent "BSc Computer Science" or "BTech Electronics." Students and courses exist without knowing which degree program they belong to.

Example: A student is in "Computer Science department" but — are they doing BSc, MSc, or BTech? No way to distinguish.

⚠ Course Locked to Single Semester

A course is linked to one specific semester. The same course taught next year to a new batch requires creating a duplicate entry — losing history.

Example: "Python 101" for 2024 batch and "Python 101" for 2025 batch are two separate unrelated courses.

⚠ Student Onboarding Has No Academic Context

Creating a user only captures Name, Email, Role, Department. No Student ID, no program enrollment, no admission year, no current semester tracking.

Example: Admin creates "Rahul Sharma, Student, CS Dept" but — which batch? Which semester? Which program? All unknown.

⚠ No Batch Identity

There's no way to group students by admission year. A 2024 batch student and a 2025 batch student look identical in the system.

Example: Both Rahul (2024 admission) and Priya (2025 admission) show as "CS Department Student" with no distinction.

⚠ Faculty Form = Student Form

The create user form shows the same fields regardless of role. Faculty doesn't need Student ID or Academic Year, but they see them. Students don't need Designation, but they see it.

Example: Role is selected last, so the form shows all fields upfront — confusing the admin.
Part 2

Proposed Solution — Hierarchical Academic Structure

A connected hierarchy where Academic Years contain Semesters, Programs define Degrees, and Courses are offered per semester with proper student mapping.

Proposed Data Model (Connected Hierarchy)

University Admin
Programs & DegreesBSc CS, BTech ECE, MSc Physics...
Academic CalendarAcademic Years → Semesters
Course CatalogMaster courses linked to Programs
ProgramDuration, Total Semesters
Academic Year2024-2025
Semester 1 & 2Auto-created
Course MasterCode, Name, Credits
Course OfferingCourse + Academic Year + Semester
+ Faculty + Capacity
Student EnrollmentStudent → Program → Batch Year
→ Current Semester → Courses

How Each Entity Works

Programs & Degrees

What: Master data. Created once per degree offered by the university.

Fields: Program Name (BSc Computer Science), Department, Duration (3 years), Total Semesters (6), Degree Type (UG/PG/Diploma)

Managed by: University Admin

Changes rarely. Only when university adds/removes degree programs.

Academic Years & Semesters

What: Time structure. Admin creates an Academic Year → system auto-creates 2 semesters under it.

Fields: Year Name (2024-2025), Start Date, End Date, Status (Upcoming/Active/Completed)

Semesters auto-created: Sem 1 (Jun-Nov), Sem 2 (Dec-May) — dates editable.

Created annually. One academic year per real year.

Course Catalog (Master)

What: Course definitions. Code, name, credits, linked to a Program + semester number.

Fields: Course Code (CS301), Name (Data Structures), Credits (4), Program (BSc CS), Semester Number (3)

Reusable: Same course used across academic years. Content updated by faculty.

Course Offering (Per Year)

What: A specific instance of a course being taught in a specific semester of a specific year.

Fields: Course (CS301) + Academic Year (2025-2026) + Semester (1) + Faculty (Dr. Sharma) + Max Capacity (120)

Students enrolled here. Different offering each year = different students, same course.

Part 4

Course Offering & Enrollment Flow

How courses are created, offered each year, and students are enrolled — without data loss across batches.

Complete Course Lifecycle

1

Admin Creates Course (Master Data)

One-time setup. Course is created as a reusable template linked to a program and semester number.

Code: CS301 Name: Data Structures Credits: 4 Program: BSc CS Semester: 3
2

Admin Creates Course Offering (Per Year)

For a specific academic year and semester, the course is "offered" — faculty assigned, capacity set.

Course: CS301 Data Structures Academic Year: 2025-2026 Semester: 1 Faculty: Dr. Sharma Max Capacity: 120
3

Admin Enrolls Students

Students from the matching batch are enrolled into the course offering. File upload with drag & drop.

Search & Select Students Drag & Drop File Upload (CSV) Capacity Check
4

Faculty Fills Course Content

On the Faculty Portal, the assigned faculty uploads syllabus, modules, assignments for this specific offering.

Syllabus Upload Module Creation Assignments
✓

Next Year — Same Course, New Offering

CS301 Data Structures is offered again in 2026-2027 with potentially different faculty, different students. No data overwrite. Previous year's offering is preserved.

Part 6

Before vs After Comparison

Aspect Current (Problem) Proposed (Solution)
Semester Creation Created standalone — no academic year context. Admin manually enters name, year, dates. Admin creates Academic Year → 2 semesters auto-created with editable dates.
Degree / Program Does not exist. No way to represent "BSc Computer Science." Programs page — master data with name, duration, total semesters, department.
Course Reuse Course locked to one semester. Must duplicate for next batch. Course is master data. "Offerings" created per year — reusable without duplication.
Student Onboarding Only Name, Email, Role, Department. No student ID, no program, no batch. Role-first form: Student ID, Program, Admission Year, Current Semester — full academic identity.
Faculty Onboarding Same form as student. No employee ID, designation, or specialization. Role-specific form: Employee ID, Department, Designation, Specialization.
Batch Identity No batch concept. All students look the same regardless of admission year. Admission Year + Program = batch identity. Can filter/group by batch.
Course ↔ Student Mapping Students enrolled per course, but no academic context. Can't tell if correct semester. Students enrolled in course offerings — linked to correct academic year + semester + program.
Data Preservation New batch overwrites old course data. No history across years. Each year has its own offerings. Previous years fully preserved.
Student Enrollment CSV CSV pasted as text in a textarea. No file upload. Drag & drop file uploader with preview and validation.
User Export Not available. Export button on users list page — download as CSV/Excel.
Part 7

MVP vs Phase 2 Scope

What we build now vs what we defer.

MVP (Build Now)

  • Programs & Degrees page (master data)
  • Academic Calendar (Academic Year → auto-create 2 Semesters)
  • Course linked to Program + Semester Number
  • Course Offerings per Academic Year
  • Role-first Create User form (dynamic fields)
  • Student: Student ID, Program, Admission Year, Current Semester
  • Faculty: Employee ID, Department, Designation
  • Remove Ministry & Research roles from dropdowns
  • Export Users button
  • Drag & drop file upload for student enrollment

Phase 2 (Defer)

  • Regulation versioning (R2020 vs R2024)
  • Syllabus version control on faculty portal
  • Allied / Elective (cross-department) courses
  • Shift 1 / Shift 2 batch management
  • Course prerequisite chains
  • Automatic course rollover across academic years
  • Ministry portal
  • Research portal

Summary

The current flat structure doesn't reflect how universities actually work. The proposed hierarchy — Programs → Academic Years → Semesters → Course Offerings → Enrolled Students — mirrors real university operations and enables proper batch management, course reuse, and academic tracking without data loss.
